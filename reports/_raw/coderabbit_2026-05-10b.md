## CRITICAL

### C1 — BubbleService.kt:1344 — Raw Thread for network I/O (L1-contribution endpoint)
`performRegen()` spawns a raw `Thread { }` for the wim-l1-contribute POST. The thread has no timeout on the `HttpURLConnection` (`connectTimeout = 5000` and `readTimeout = 5000` are set, but the thread itself is non-daemon and holds a reference to `BubbleService.this@BubbleService`). If the Cloud Function is slow or the network stalls at the TCP layer past the read-timeout window, the thread lingers and keeps the Service context alive after `onDestroy()` has fired, producing a leaked-context crash on next GC cycle. Same pattern at BubbleService.kt:3942 (L1-detect guess thread).
Fix: use `scope.launch(Dispatchers.IO)` with `withContext` like every other network call in the file.

### C2 — BubbleService.kt:3795-3798 — Infinite coroutine loop never cancels
The TurboTax progress loop (`while (true) { showPipelineStage(...); delay(2000) }`) launched inside `scope.launch` is cancelled by `turboTaxJob?.cancel()` only on the happy path. If `ReconstructClient.reconstruct()` throws, the catch block at line 4097 runs `turboTaxJob` is `null` by that point if the cancel already happened — but if the throw occurs before the coroutine's first suspension point inside the turboTax launch, the `turboTaxJob?.cancel()` at line 3850 is never reached because control jumped straight to catch. In practice the coroutine is still running, `showPipelineStage` keeps firing after the error toast, and the transcript bar keeps overwriting the error message every 2 seconds until the service dies.
Fix: wrap the entire `scope.launch` block in `try/finally { turboTaxJob?.cancel() }`.

### C3 — ReconstructClient.kt:699 — `reconstructWithSonnet` runs on the calling thread (blocking IO)
`reconstructWithSonnet` is a regular `fun`, not a `suspend fun`. It calls `http.newCall(request).execute()` synchronously. Its only caller, `reconstructDirect`, is inside `withContext(Dispatchers.IO)`, so in the current code this happens to run on an IO thread. But `reconstructWithSonnet` is `private`, and any future refactor that calls it from a Main-thread path (e.g., a unit test, a Compose preview coroutine) will silently block the main thread with no compile-time warning. Function should be `private suspend fun` with `withContext(Dispatchers.IO)` wrapping the execute call.

### C4 — BubbleService.kt:3965-3988 — `conn.disconnect()` only called on some code paths
The `wim-l1-guess` Thread has three `conn.disconnect()` calls on specific branches but misses the `responseCode != 200` branch that falls through to `conn.disconnect()` correctly. However there is no `finally` block, so if `conn.inputStream.bufferedReader().readText()` or `org.json.JSONObject(responseText)` throws, `conn` is never disconnected, leaking a socket. The outer `catch (_: Exception) {}` swallows it silently.
Fix: wrap in try-with-resources or a `try { ... } finally { conn.disconnect() }`.

## HIGH

### H1 — MultiPassDecoder.kt:131-136 — `toMap()` on duplicate keys silently drops entries
`lowConfLogprobs` is built by `flatMap(...).toMap()`. If two low-confidence segments contain the same alphanumeric-only token (common for repeated words like "the", "I", "and"), only the last mapping survives. This means a word that appears in both a low-confidence and a high-confidence segment will silently get whichever segment happened to be last in the list — possibly assigning the wrong logprob or missing it entirely.
Fix: use `groupBy` + `minByOrNull { it.second }` to keep the lowest (worst) logprob per token, since that's the conservative signal you want for flagging.

### H2 — L1PackHelper.kt:61 — Cache stores `null` on failure but never retries
`cache[language] = null` on any IO/parse exception. Every subsequent `loadPack()` call returns early with `null` via `cache[language]?.let { return it }` — but `null` is not a cached `Pack`, it's a missing value. The `let` only fires when the value is non-null, so the `null` is not returned via that branch; instead `cache[language]` returns `null` which satisfies the `if (cache.containsKey(language))` check ... except that check doesn't exist. The actual code goes to `cache[language]?.let { return it }` — when the value is `null`, `let` doesn't run, so the function falls through to re-open the asset every time. This means every call after a failure re-attempts the file open. Not a correctness bug (the retry is fine) but it destroys the purpose of the cache. The comment says "Loaded once" but the null-caching doesn't actually prevent re-loading.
Fix: `if (cache.containsKey(language)) return cache[language]` before the try block.

### H3 — BubbleService.kt:1606-1614 — Audio focus abandoned unconditionally after 600ms
`audioManager?.requestAudioFocus(focusRequest)` is called and then unconditionally abandoned after 600ms via `timerHandler.postDelayed`. If the recording is stopped within those 600ms (short utterance, user taps again), the abandon fires after `audioRecorder` is already released, causing an `abandonAudioFocusRequest` against a stale request. On some Samsung builds this triggers a `NullPointerException` in the audio focus stack. The `focusRequest` is a local variable so there's no way to cancel the delayed abandon if recording ended early.
Fix: store the `focusRequest` as a field and explicitly abandon it in `stopAndProcess()` instead of via a timer.

### H4 — WimApp.kt:228-253 — Toast from Application.onCreate on a background thread
The `mainHandler.post { Toast.makeText(...) }` correctly runs on the main thread. But `WhisperLocalModelDownloader.downloadAndUnpack` is launched in `appScope` (Dispatchers.IO), and the progress callback at line 238 is invoked from the IO thread. Inside the callback, the condition `if (progress.stage == "Ready")` dispatches back to `mainHandler.post`, which is safe. However if `downloadAndUnpack` itself throws before calling the callback, the exception is silently swallowed by the coroutine (no `catch`). The model download then fails silently with no user-visible error — the app keeps using the Android SpeechRecognizer fallback forever with no indication to the user of why.
Fix: Add `catch (e: Exception)` to the `appScope.launch` block with a fallback Toast.

### H5 — BubbleService.kt:3487-3512 — New `OkHttpClient` created per Command Mode call
`callBackendCommandTransform` and `callOpenAiTransform` each build a fresh `OkHttpClient`. `OkHttpClient` creates its own thread pool and connection pool. Creating one per request is a well-known Android perf anti-pattern that exhausts file descriptors on sustained use. `ReconstructClient` correctly shares a singleton `http` client.
Fix: use `ReconstructClient`'s shared `http` client, or create a module-level singleton in BubbleService for the command-mode paths.

### H6 — BouncerActivity.kt:157 — `Build.MANUFACTURER` comparison is unreliable
`Build.MANUFACTURER.equals("samsung", ignoreCase = true)` used in three places (lines 157, 292, 305) to detect Samsung devices. This string varies across carrier builds ("Samsung", "SAMSUNG", "samsung Electronics", "SAMSUNG ELECTRO-MECHANICS"). The `ignoreCase = true` handles case but not the prefix-only forms. Google's recommendation is to check `Build.BRAND` or to use a utility that normalizes these.
Risk: Samsung sleep page silently skipped for a non-trivial fraction of Samsung users with carrier-modified builds.

### M4 — ReconstructClient.kt:566-568 — L1 prompt injected twice at L2/L3

### M6 — BubbleService.kt:3860-3878 — LLM leak patterns use substring containment, not word-boundary match
`pattern in reconLower` (line 3873) matches anywhere in the string, including inside words. For example, `"i apologize"` would fire on the reconstructed text `"she said i apologize for the delay"` — a legitimate dictation that the user will never see because it gets silently replaced with the raw ASR. Using `startsWith` for the initial check and `in` for the rest is inconsistent and over-aggressive.
Fix: use `Regex("\\b${Regex.escape(pattern)}\\b")` for word-boundary matching, or at minimum require the pattern to start at the beginning of the output string for all entries.

### M7 — BubbleService.kt:4063-4070 — MultiPassDecoder runs after injection on L2+ with `lastWavFile`
The clarifier's multi-pass check reads `lastWavFile` after `injectText` has already run (line 3907). The WAV file is cleaned up in `setBubbleIdle()`, which is called later. This ordering is correct for the happy path. But if the clarifier `enterClarifierCycle` takes a long time (user ignores it for 20+ seconds), and the user starts a new recording, `setBubbleIdle()` from the prior cycle's `onExit` may delete the new session's WAV. The `lastWavFile` reference is overwritten at line 3805 in `stopAndProcess()`, so the old WAV's `File` reference is orphaned but the new WAV's file is then deleted by the old cycle's `onExit` via `setBubbleIdle()` → `lastWavFile?.delete()`.
Risk: the second recording's WAV is deleted before it can be read, silently falling back to on-device text.

### L1 — BubbleService.kt:506-507 — `getSystemService` called inside accelerometer sensor callback (every sensor event)
`getSystemService(PowerManager::class.java)` and `getSystemService(KeyguardManager::class.java)` are called on every `onSensorChanged` event (~100 Hz with `SENSOR_DELAY_GAME`). These are cheap but non-trivial cache lookups. Cache them as fields in `onCreate` or as local variables in `setupShakeDetector`.

### L2 — MultiPassDecoder.kt:56-57 — `primary` falls back to an empty `TranscribeResult` instead of the first pass
If `deferred.awaitAll()` returns an empty list (all temperatures failed), `primary` is `TranscribeResult(text = "", asrMs = 0)`. This is fine. But if the temperatures list is non-empty and all passes throw, `awaitAll()` itself throws, so the empty-list case is actually unreachable — the catch is upstream. The `firstOrNull()` null-check adds dead code. Not harmful, just misleading.

### L3 — WimApp.kt:34 — `bundledKey()` reads API key from assets in DEBUG only, but the assets may still ship
`if (!BuildConfig.DEBUG) return ""` prevents reading the key in release. However if `api_key.txt` or `anthropic_key.txt` were accidentally added to `assets/` and the release APK is built, the file still ships inside the APK (it's just never read). The `.gitignore` for these files is the real protection; this code doesn't help if someone does `aab/aab extract`. Not a runtime bug, but worth a build-time `BuildConfig.DEBUG` check at the asset level (via `productFlavors` or an `excludes` in the release variant).

### L4 — BouncerActivity.kt:63-65 — `POST_NOTIFICATIONS` permission requested with `requestPermissions` but result not used
`onRequestPermissionsResult` calls `refreshPermissions()` which checks `checkSelfPermission(POST_NOTIFICATIONS)` — that part is correct. But if the user denies and selects "Don't ask again," subsequent taps on `permNotifications` still call `requestPermissions`, which silently no-ops on Android 12+ without showing any dialog. The row never gets a "go to settings" tap hint to open the App notification settings page.

### L5 — ReconstructClient.kt:649 — `checkCriticalTokens` regex misses negative numbers and ranges
`Regex("""\$?\d[\d,.]*%?""")` matches `$5`, `100`, `3.14%`. It does not match `-5`, `(3)`, or `10-20`. These edge cases probably don't matter for common dictation, but are documented here for completeness.

### L6 — BubbleService.kt:1360-1364 — `conn.disconnect()` called then result used
In the L1 contribution thread, `conn.disconnect()` is called at line 1361, immediately before `conn.responseCode` (the trigger call) on line 1362. `HttpURLConnection.disconnect()` before `getResponseCode()` releases the underlying socket. Depending on the JVM implementation, `getResponseCode()` after `disconnect()` may silently return the cached code or throw. The actual request was already sent by `outputStream.write(payload)`, so the data is in flight, but the response-code read is unreliable.
Fix: move `conn.responseCode` before `conn.disconnect()`, or just call `conn.disconnect()` in a `finally` block without reading the response code (fire-and-forget is the stated intent).
