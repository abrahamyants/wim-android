## 1. First-Run Onboarding (BouncerActivity)

### What's there

All 5 permission gates exist in code and layout:
- `permOverlay` — draws over apps
- `permAccessibility` — text injection
- `permMic` — voice recording
- `permBattery` — battery optimization
- `permNotifications` — foreground service (Android 13+)

Auto-advance logic: `refreshPermissions()` gates all 5 and only calls `showPage(pageTier)` once all are granted. This is correct.

Back navigation is implemented for every page via `onBackPressedDispatcher`. The permissions page is the hard floor — back there does nothing, which is correct (can't go further back in onboarding).

Samsung deep-sleep page is shown only on `Build.MANUFACTURER == "samsung"`. Z Flip 7 will hit this.

### Issues

**P1 — Permission subtitle copy is minimal, not motivating**  
Each permission row shows a 2-3 word subtitle (e.g. "draw over apps", "stay alive", "voice recording"). No WHY. The accessibility permission is the most sensitive — the only one with slightly better copy is the accessibility row, which shows `"Installed Apps → What I Meant → Allow"` as a navigation hint. The others get nothing explanatory. A new user who doesn't already trust the concept may deny accessibility here because nothing on the row explains why a keyboard-style app needs it. Should be 1 sentence per row explaining what breaks without it.

**P2 — Auto-advance requires ALL 5 permissions before tier page appears**  
If the user grants 4/5 and the system denies notifications silently (common on older ROMs), they are stuck on page 1 with no forward button and no explanation of which one is blocking. The `!` indicator shows which rows are pending, but there's no explicit "X of 5 complete" counter and no fallback "skip notifications" path. Notifications is the least critical permission but currently a hard gate.

**P2 — `bouncer_free` vs `bouncer_upgrade` naming is opaque**  
"Free" and "Upgrade" as tier names aren't anchored to concrete capability differences on the page. The descriptions are decent (`bouncer_free_desc`: "on-device, cleans disfluencies, offline"; `bouncer_upgrade_desc`: "AI reconstruction, learns your vocabulary") but there's no price shown anywhere on the upgrade card. A user who taps "Upgrade" gets the tone page — then ends up with `tone=professional` in prefs but no indication that upgrade requires a subscription or is actually free-at-launch. If the tier is invite-only, that's not communicated.

**P3 — Gesture reference card (pageBubble) teaches 6 gestures in one read-only list**  
Tap, Hold, Double-tap, Drag, Fling, Shake are all listed as text rows with no visual affordance and no interactive demo. The user reads this once and then has to remember it. The spec calls for a live demo (`BubbleDemoScript`) that fires after `ONBOARDING` action — but that only runs after the user taps "Launch" on the final page. By that time they've already committed. The gesture card on pageBubble (page 4 of 8) is the last education moment before the demo but is static. The onboarding vision spec (`project_wim_onboarding_vision.md`) explicitly wants the bubble as Mr. DNA and interactive demo — this page is still a static table.

**P3 — Samsung deep-sleep page page indicator says "6/6" but there are 7/8 pages**  
`pageSamsungSleep` uses `bouncer_slide_6_6` as its indicator string and `pageFinal` also uses `bouncer_slide_6_6`. Both read "6/6". Samsung users see two consecutive "6/6" slides. Non-Samsung users see the slide numbering stop at "6/7" on `pageAutoSend` (which uses `bouncer_slide_6_7`), then jump to a final page with "6/6". The slide counter is inconsistent across paths and will confuse users.

**P3 — No dead-end recovery if user leaves and returns mid-flow**  
`hasAdvancedFromPermissions` is an in-memory flag. If the user exits BouncerActivity and returns (e.g. to grant a system permission in Settings), `onResume` calls `refreshPermissions()` and will re-trigger auto-advance. That's actually correct behavior. However, if `onboarding_complete` was written to prefs (it isn't until `launchBubbleOnboarding()` fires) but the flow was interrupted, the user would land on MainActivity with no bubble. This sequence isn't possible with the current code, but worth noting.

## 2. Core Recording Flow

### What's there

**Tap handling** (BubbleService.kt, line ~1091–1135):
- Single tap: 300ms deferred. First tap queues `deferredSingleTapAction`; second tap within 300ms pre-empts and opens menu. After 300ms, `startPulseRings()` + `startListening()` fire.
- Hold (500ms): immediate recording + haptic on threshold. Release stops. This is correct.
- `startPulseRings()` fires BEFORE `startListening()` — the visual is immediate.

**Pipeline stage labels** via `showPipelineStage()`:
- Transcribing: `"⏳ Transcribing" / "Sending audio to Whisper"` (line 1783)
- Stripping: `"⊛ Cleaning up..." / "Removing disfluencies & fillers"` (line 3583)
- Reconstructing: `"⊛ Reconstructing intent..." / "$tone tone · L$layer $layerLabel"` (line 3724)
- Reviewing (multi-pass): `"⟳ Reviewing" / "Cross-checking unsure words"` (line 3939)
- Verified/injected: Falcon label + word-count + ms (line 3841)

**L4 TurboTax engagement**: When layer ≥ 4, a coroutine cycles through 5 stage messages at 1200ms intervals during reconstruction (lines 3728–3741). Covers the "what does the user see if reconstruction takes 10 seconds" case explicitly for L4.

**SEND_READY**: Label changes to `"SEND"` in green (0xFF5AD15F), `bubbleTime` shows countdown `"Ns"` ticking every 250ms, bubble optionally facehugger-jumps to Send button. 5-second timeout, auto-reverts to IDLE. Clear enough.

### Issues

**P0 — 300ms single-tap latency before recording starts**  
Every single tap to start recording is delayed 300ms by the double-tap timeout window. The pulse rings fire immediately, but `startListening()` is deferred. On Android, the mic takes ~50-100ms to open after the call. So the actual first-words capture starts ~350-400ms after the tap. On L2-L4, the pre-roll buffer (`audioRecorder?.primeBuffer()`) is supposed to mitigate this — but the pre-roll is only primed when `WimApp.apiKey().isNotBlank() && WimApp.layer() >= 2` (line 1191). At L1, and for any signed-in user at L1 (the post-onboarding default), there is no pre-roll and the 300ms delay is a real gap. First word is frequently lost. The pulse rings starting before `startListening()` creates a visual lie: the rings say "I'm listening" before the mic is actually open.

**P1 — Network failure on Whisper shows "Error" with no user action path**  
On Whisper exception (line 1823-1840): `showPipelineStage("Error", "Transcription failed")` then `setBubbleIdle()` after 2000ms. The user sees "Error / Transcription failed" for 2 seconds and then IDLE. No retry affordance. No explanation of cause (network vs API key vs quota). No distinction between a recoverable network blip and a broken API key. The label reverts to IDLE automatically without giving the user a chance to decide what to do.

**P1 — Reconstruction failure silently falls back to raw text**  
On `ReconstructClient` exception (line 3975-4014): raw pre-cleaned text is injected, a Toast says "Reconstruction failed — raw text used", and `setBubbleIdle()` fires. The bubble's visual feedback during this path: the stage arc was at stage 1 (Reconstructing), reconstruction throws, the catch injects raw text and goes idle — the user sees the pipeline advance mid-arc, then the bubble just returns to IDLE with a Toast. The bubble label never shows a failure state for reconstruction. `BubbleStateBus.advance(BubbleState.Failed(...))` is NOT called in the reconstruction catch block — so the FSM stays in `Reconstructing` state while the text is silently inserted. That's a state/UX mismatch.

**P1 — No active text field: inject silently fails, user gets no feedback on bubble**  
When `WimAccessibilityService.instance == null` (line 3865-3868), a Toast fires (`getString(R.string.toast_enable_accessibility)`) but the bubble just goes to IDLE — no label change, no "FIX" or "PERM" state. The user sees the pipeline run to completion, then the bubble sits at IDLE with text apparently injected but nothing appeared in their text field. The only feedback is a Toast that may disappear before they look. This is the most common new-user error path ("I set it up but nothing appeared") and it has the weakest feedback.

**P1 — When accessibility service IS running but no field is focused, inject also silently fails**  
`WimAccessibilityService.instance?.injectText(rawText)` — if the service is alive but there's no focused text field, injectText presumably no-ops or fails silently. The bubble doesn't know. No `INJECT_FAIL` reason is surfaced in the FSM. This produces the same invisible failure as above.

**P2 — SEND_READY state: what tap target is the bubble?**  
When facehugger is active, the bubble has jumped to the host app's Send button. The user is now looking at a small knob sitting on top of the Send button. The instruction is "tap me to send." But the bubble (72dp) is sitting on top of the Send button — tapping the bubble sends. This is correct by design. However: if facehugger is NOT active (either because `facehugger_send_enabled` is off, or because `getSendButtonCenter()` returned null), the bubble stays wherever it was. The user sees "SEND / 5s" with no arrow or position cue pointing toward where to tap. The SEND label is the only signal. Fine for return users; confusing first time.

**P3 — L1 pipeline stage labels during cloud-ASR path**  
When the user is on L1 with `l1CloudAsr()` true, the transcription goes to Whisper, the label says `"⏳ Transcribing / Sending audio to Whisper"`. Then `processText()` fires with `setBubbleProcessing()`. But L1 doesn't call `BubbleStateBus.advance(BubbleState.Transcribing...)` for the on-device path — it reads `lastRawText` 400ms after stop. In that 400ms window, the bubble shows whatever label was set by `setBubbleProcessing()`. The on-device L1 path has no "Transcribing" stage visible to the user — it just shows PROC until text arrives.

## 3. Clarifier UX

### What's there

- `Clarifying` state: bezel split into green (left/✓) and red (right/✕) halves, hidden by default.
- `paintClarifierLabel()` sets `bubbleLabel` to `"WORD?"` (uppercase, 8-char max) in gold.
- `bubbleTime` shows `"idx+1/total"` (e.g. "1/3").
- `TranscriptBarController` shows: `"did you mean → CANDIDATE · ↓ hold = skip"`.
- Tap-left = approve (`ClarifierController.approve()`), tap-right = reject, hold 500ms = defer/next.
- Voice commands: "yes/approve/ok/confirm" or "no/reject/cancel/nope" or "next/skip".
- Flash affects: `bubbleAffect?.emitApproveFlash()` / `emitRejectFlash()`.
- HEAD_TILT affect: knob tilts 0→8° on entry.
- Timeout: fires `clarifierTimeout` runnable — retries once, then dismisses.
- Entry: `enterClarifierCycle()` flashes all arcs orange for 320ms, then `ClarifierController.enter()`.

### Issues

**P1 — Left=approve, right=reject is not discoverable without reading onboarding text**  
The split bezel shows ✓ on the left and ✕ on the right, but these are 18dp TVs at `layout_marginStart/End="1dp"`. On a 72dp bezel rendered at ~216px, these symbols are very small. The `bubbleLabel` shows the word with `?` but the green/red halves and the tiny ✓/✕ are the only directional cues. The transcript bar hint (`"did you mean → CANDIDATE"`) doesn't explicitly say "tap left to accept." A first-time user may tap the center knob (which fires the normal tap-routing path, not the bezel ring check) and accidentally do nothing or start a new recording.

The tap zone for the clarifier is `dist > innerR && dist < outerR` (bezel ring, not knob). Knob taps at `dist <= innerR` fall through to the normal tap handler, which would try to start a recording (deferred single tap). During `Clarifying` state, this would hit `BubbleStateBus.advance(Listening)` — which IS allowed from Clarifying per the FSM (clarifier exits as REJECT-all). That's an accidental full-exit of the clarifier caused by a slightly off-center tap.

**P1 — Hold-to-defer requires 500ms hold during Clarifying, but the same 500ms hold during non-Clarifying starts recording**  
The code (lines 1076-1088) checks `pressDurationMs >= 500L && BubbleStateBus.current() is BubbleState.Clarifying` — this fires in `ACTION_UP`, which means the user must hold for 500ms AND release. But the `holdStartRunnable` (line 785) at 500ms also fires `startListening()` during any non-clarifying state. During Clarifying, `holdModeActive` is set to true in the `holdStartRunnable` closure only if `!isRecording`. So if the user holds during Clarifying, `holdStartRunnable` fires after 500ms, sees `!isRecording` is true, sets `holdModeActive = true`, and calls `startListening()` — which ALSO advances state to `Listening` from `Clarifying`. This means the hold gesture during Clarifying exits the clarifier entirely (recording starts) rather than defer-advancing. The defer path at `ACTION_UP` only fires if `holdModeActive` is false — but by 500ms into a hold, `holdModeActive` is already true. **Hold-to-defer is functionally broken.** The hold triggers recording before `ACTION_UP` can check for defer.

**P2 — No timer shown for when the clarifier will auto-dismiss**  
The clarifier has a timeout that retries once then dismisses (via `clarifierTimeout` runnable). The user has no visual indicator of how much time is left before it disappears. The `bubbleTime` shows `"idx/total"` progress, not a countdown. A confused user who does nothing will have the clarifier disappear with no explanation.

**P2 — Clarifier word label truncated at 8 chars**  
`flag.originalWord.uppercase().take(8)` — on a 44dp inner knob with 10sp font, 8 chars is already tight. A word like "DISFLUENCY" becomes "DISFLUENC?". The truncation gives no hint that the word was cut. User may not recognize what word is being questioned.

## 4. Error States

### Issues

**P0 — Reconstruction failure: FSM is in `Reconstructing` state, UX shows IDLE**  
Covered above. The catch block at line 3975 injects raw text and calls `setBubbleIdle()` without first calling `BubbleStateBus.advance(BubbleState.Failed(...))`. The FSM state machine has `Reconstructing → Failed` as a valid transition, but it's never used in the cloud reconstruction failure path. The bubble goes IDLE while the FSM believes it's still `Reconstructing`. Any code observing `BubbleStateBus.state` (BubblePersona, BubbleAffect observers) will be in the wrong state after this.

**P0 — No text field focused: bubble shows IDLE after silent injection failure**  
Detailed above. The `WimAccessibilityService.instance == null` path shows a Toast and goes IDLE. The `instance != null` but no focused field path has no feedback at all on the bubble — just IDLE.

**P1 — "Error / Transcription failed" gives no recovery instruction**  
The 2-second error banner doesn't tell the user what to do. Is the API key wrong? Is there no network? Should they retry? The bubble auto-reverts to IDLE. Compare to the `alertOnMissingPermissions()` path (line 4132) which shows `"FIX"` + `"PERM"` on the bubble label and fires a notification with badge — that's P0-level treatment for permissions. The same treatment isn't applied to network failures during transcription.

**P1 — Whisper hallucination ("∅ Silence / Nothing to transcribe") is technically correct but user-facing copy is wrong**  
The hallucination path (line 1812) fires when the model hallucinates (e.g. no real speech was recorded, but Whisper still produced tokens that match hallucination patterns). The label `"∅ Silence"` implies the user was silent. But the user may have spoken and the audio was just too short or quiet — the hallucination detector fired false positive. The user sees "Nothing to transcribe" and doesn't know if the mic didn't capture them, if they were too quiet, or if something broke.

**P2 — `alertOnMissingPermissions()` fires 600ms after bubble shows (line 701)**  
This is a reactive check — bubble appears, then 600ms later it checks accessibility + mic and shows a Toast + "FIX/PERM" label if missing. The delay is intentional (to not flash immediately on spawn) but 600ms is long enough that the user may have already tapped the bubble before the alert appears. The FIX/PERM label would then be overwritten by REC state.

**P3 — Auto-send failure ("Couldn't find Send button") via Toast only**  
When `actuallySend()` fails (line 1398-1401), it shows `Toast.makeText("Couldn't find Send button")` and goes IDLE. The bubble doesn't show any failure state. After the bubble was green and sat on the Send button for 5 seconds, the user taps it, nothing gets sent, the bubble goes IDLE with a Toast. Should show `"✕ SEND FAIL"` on the bubble label for 2 seconds.

## 5. Settings and Profile (MainActivity)

### What's there

Layer selection: 4 card rows labeled `"I. Transcribe"`, `"II. Reconstruct"`, `"III. Profile"`, `"IV. Speech Disfluency"`. Each is a selectable card. Current selection is highlighted.

### Issues

**P1 — Layer labels don't explain the functional difference to a new user**  
`"I. Transcribe"` vs `"II. Reconstruct"` vs `"III. Profile"` vs `"IV. Speech Disfluency"` — the Roman numerals imply an ordering but the labels themselves don't answer "what does choosing III give me that II doesn't?" There are string entries `layer_1_title` through `layer_4_title` in strings.xml but no `layer_1_desc` through `layer_4_desc`. The layer cards in the layout need expansion text. A user who arrives from onboarding at L1 (the default) sees "I. Transcribe" selected but doesn't know to upgrade to II for AI reconstruction unless they read the upgrade option they already chose on pageTier. The connection between the tier choice in onboarding and the layer selection in MainActivity is not surfaced.

**P2 — No Facehugger Send toggle visible label or description**  
The spec (`project_wim_facehugger_positioning.md`) refers to `facehugger_send_enabled` as a user-visible toggle. In MainActivity, this setting presumably exists somewhere in the bubble section. Static analysis of the layout was not done for all of MainActivity's scrollview, but the strings.xml doesn't contain a user-facing label for "Facehugger Send" that would be distinct enough for a non-technical user to understand. If the toggle exists, the label should be "Bubble jumps to Send button" not a technical name.

**P2 — Work/personal toggle on the bubble bezel is undiscovered after onboarding**  
The bezel ring left/right tap toggles `isWorkMode`. Tapping left of center = Work (professional tone), right = Personal (casual). This is active in normal (non-Clarifying) state. There is no persistent visual indicator on the bubble showing which mode is active. The `updateBezelLabels()` presumably updates something, but without reading that function, the static label ("IDLE") doesn't distinguish work vs personal. A user who set tone during onboarding has no feedback that tapping the bezel ring changes their tone profile in real time.

**P3 — "INSTANT mode" is a pref (`instant_mode`) accessible nowhere in the visible UI**  
Line 3524: `if (WimApp.prefs.getBoolean("instant_mode", false))` — bypasses all processing and pastes raw ASR. No UI surface for this in MainActivity or the bubble menu per the strings.xml scan. This is either a developer/test flag that should be removed from production or a power-user feature that needs a settings row.

## P0 Critical Items (must fix before any external testing)

1. **Reconstruction failure FSM mismatch** — `BubbleStateBus.advance(BubbleState.Failed(FailReason.NETWORK))` must be called in the reconstruction exception catch before injecting fallback text. Observers are currently left watching a `Reconstructing` state that never resolved.

2. **No text field feedback on bubble** — When `WimAccessibilityService.instance == null`, the bubble must show `"FIX" / "PERM"` label (reuse the existing `alertOnMissingPermissions()` path) rather than going silently IDLE. When the service exists but injection fails, `Failed(INJECT_FAIL)` should advance and the label should show "✕ FAIL" for 2 seconds.

3. **300ms tap-to-mic latency** — Pre-roll the AudioRecorder on bubble show for ALL layers (not just L2+ cloud). The mic should be primed before the tap lands. Move `primeBuffer()` call out of the layer≥2 gate.

## Hold-to-Defer Bug Detail

The bug at item 13 is worth spelling out precisely. In `ACTION_DOWN`, `holdStartRunnable` is posted at `HOLD_THRESHOLD_MS` (500ms). That runnable checks `!isDragging && !isRecording` — both true during Clarifying — and calls `startListening()`. This fires BEFORE `ACTION_UP`. So by the time `ACTION_UP` fires 500+ms later, `holdModeActive` is `true`, and the code takes the `holdModeActive` branch (line 925: `if (holdModeActive) { holdModeActive = false; if (isRecording) stopAndProcess() }`). The defer check (lines 1076-1088) is never reached because `holdModeActive` short-circuits `ACTION_UP`.

Fix: in `holdStartRunnable`, check `BubbleStateBus.current() is BubbleState.Clarifying` and skip `startListening()` + `holdModeActive = true` if true. The defer should be handled purely in `ACTION_UP` by inspecting `pressDurationMs` — but for that to work, the hold runnable must not set `holdModeActive` during Clarifying state.
